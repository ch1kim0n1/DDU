# DDU Mirror Experience System Card

Version: 0.1.0
Surface owner: Engineer D — 3D, UI, and voice
Backend contract: Mirror Findings Contract 1.0.0

## Intended use

DDU Mirror is a defensive self-exposure viewer. It helps a person understand
how their own verified public identifiers and voluntarily supplied evidence
could be linked, which attack paths those exposures enable, and which
remediations are reversible.

It is intended for self-audit, security education, and consent-driven privacy
hardening. It is not a target-search interface.

## Interface claims

- A node’s Z position represents `hop_depth`.
- Height and glow represent persona-adjusted `severity_score`.
- Colour preserves the finding’s verification state.
- Lit paths are supplied by the backend attack-path recompute.
- Rejected and contradicted findings contribute zero and are suppressed from
  the active scene and voice grounding.
- Remediation simulation is non-mutating. Irreversible findings refuse to be
  marked fixed.
- Evidence is redacted by default. Raw values require a scoped reveal token.
- Session wipe feedback uses destroyed counts returned by the backend.

## Human control

Every discovery expansion begins as a proposal. The interface shows its
rationale, expected findings, external systems, and hop depth before the user
can approve or reject it. Commands are sent over the session WebSocket, with a
REST fallback. The server’s state machine refuses execution unless the
proposal is approved or edited.

The **That’s not me** control prunes optimistically for immediate feedback, then
replaces that local projection with the server’s recomputed snapshot.

## Voice data flow

```text
user-approved audio
  → ElevenLabs speech-to-text
  → local typed-placeholder PII scrub
  → voice-tier LLM with de-identified finding allowlist
  → local output scrub
  → ElevenLabs text-to-speech
  → browser playback
```

The raw transcript is not returned to the browser, logged, or included in an
LLM prompt. Session-specific handles, email addresses, account URLs, phone
numbers, IP addresses, coordinates, card numbers, SSNs, street addresses, and
common URL forms are replaced with typed placeholders.

When ElevenLabs is not configured, the UI refuses microphone transcription,
continues to support typed grounded questions, and uses browser speech
synthesis. When the LLM provider is offline, answers are generated by a
deterministic local grounding path and labelled as a fallback.

## Safety controls

- No arbitrary target field exists.
- Findings are scoped to the session’s verified subject.
- Third-party identifiers are suppressed upstream.
- Untrusted scraped text is parsed in a tool-less quarantine tier.
- All model-facing finding payloads use an explicit field allowlist.
- Reveal operations are scoped, authenticated by HMAC tokens, and logged.
- Irreversible findings require a compensating control in the schema.
- Map markers are privacy-jittered; exact coordinates remain behind reveal.
- Session wipe destroys the Redis/in-memory findings graph and raw-value vault.

## Known limitations

- Production mode verifies signed OIDC/JWKS or internal HS256 identity
  assertions. Offline development mode still permits a clearly-labelled local
  identity so tests do not depend on an identity provider.
- Approval uses real LangGraph interrupts with Redis, SQLite, or in-memory
  checkpointers.
- Redis sessions are encrypted, TTL-bound, conflict-checked, and shared across
  workers; Redis Pub/Sub fans state changes out to every WebSocket worker.
- Browser speech synthesis varies by platform.
- Map positions are intentionally illustrative until a user explicitly
  reveals a coordinate.
- Cached HIBP/Sherlock and mock findings remain suitable for a disclosed demo,
  not evidence of a live scan. Strict production mode refuses those fallbacks.

## Evaluation

Automated checks cover:

- rejection cascades, score recomputation, and path pruning;
- irreversible remediation refusal;
- reveal-token enforcement and outbound PII blocking;
- voice transcript scrubbing and exclusion of rejected findings;
- WebSocket plan/approve materialization;
- production TypeScript build.

Visual usability, keyboard flow, microphone behaviour across browsers, and
screen-reader announcements still require manual cross-browser QA before a
public release.
